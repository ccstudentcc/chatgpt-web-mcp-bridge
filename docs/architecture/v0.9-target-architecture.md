## 1. Scope And Non-Goals

### 1.1 In Scope

- This document defines the target architecture and the allowed migration path. It does not by itself authorize immediate implementation of every target capability.
- ChatGPT Web only
- Chrome Extension as the final browser shell
- A split-kernel design with:
  - Extension-owned ChatGPT runtime orchestration
  - Gateway-owned execution semantics
- A dual-mode execution model:
  - `reviewed`
  - `yolo`
- A builtin-first capability model
- `run_pwsh` as a first-class power tool
- External MCP as a pluggable extension ring, not the default core

### 1.2 Out Of Scope

- Multi-platform browser AI support
- Conversation management as a product pillar
- Browser credential, cookie, history, or debugger access as a core feature
- Remote MCP auto-execution as a default workflow
- Store, marketplace, remote config, or analytics as core architecture goals

### 1.3 Current Authorization Gate

As of April 27, 2026, the old v0.1 close-out gate is no longer blocking v0.9 work. The target surfaces described here are now eligible implementation surfaces, but they are still not blanket permission to start everything at once.

Current rule:

- concrete v0.9 work must still be sequenced in root task-control docs
- the proven runtime baseline must be preserved or explicitly migrated
- broad capability rollout must not hide unresolved boundary work

## 2. Core Architecture Principles

### 2.1 Split-Kernel Architecture

The system must be split into two hard ownership zones:

- `Extension runtime`: owns everything that depends on real ChatGPT page behavior
- `Gateway kernel`: owns everything that depends on tool execution, policy, audit, and caching

The project must not collapse back into a single browser-side script that mixes page runtime logic with execution semantics.

### 2.2 ChatGPT Runtime Belongs To The Extension

The extension owns:

- Hidden request-layer injection
- Assistant turn detection
- Invalid-turn classification
- Startup/history rescan
- Duplicate guard
- Result delivery back into the composer
- Operator-facing runtime state

The gateway must not depend on DOM selectors, composer state, send button state, or other ChatGPT page internals.

### 2.3 Execution Semantics Belong To The Gateway

The gateway owns:

- Tool registry and catalog materialization
- Tool policy and risk evaluation
- Builtin tool execution
- Proposal flow
- `run_pwsh`
- External MCP lifecycle and tool proxying
- Result cache
- Audit log
- Diagnostics

The extension must not implement builtin tool logic, proposal apply, shell execution, or external MCP lifecycle.

### 2.4 Fallback Is Not A Second Architecture

Fallback and recovery paths must reuse the same contracts and state model as the main path. They must not become a parallel execution system.

### 2.5 Long-Term Truth And Task-Time Truth Must Stay Separate

- `docs/prd.md` defines the closed runtime reference baseline
- This document defines target-state architecture truth
- Task documents explain the current work item

Task documents must not redefine long-term architecture boundaries.

### 2.6 Compat Must Only Get Thinner

Any compatibility layer exists only to bridge old entrypoints to target contracts. It must not become the place where new behavior lands first.

## 3. Three-Ring Model

### 3.1 Final Core

This is the part that must stabilize first.

Extension core:

- `chatgpt-adapter`
- `injection-runtime`
- `turn-runtime`
- `result-delivery`

Gateway core:

- `execution-kernel`
- `tool-registry`
- `tool-policy`
- `builtin core tools`
- `shell-runtime`
- `audit-log`
- `diagnostics`

Shared core:

- `protocol`
- `turn-model`
- `policy-model`
- `result-model`

### 3.2 Extension Ring

This ring is part of the final system, but it must not block core convergence.

- Full proposal workflow
- External MCP
- Full result cache UI and search
- Extended git and process tools
- Richer operator panel and diagnostics views

### 3.3 Compat Ring

This ring is transitional only.

- Temporary compatibility around current live gateway contracts, including `/tools`, until any approved dual-route migration is explicitly documented
- Temporary type mapping layers
- Temporary gateway composition roots that only adapt old entrypoints
- Thin bridge-only shims may exist temporarily while the live baseline is being replaced, but a dedicated `apps/userscript-compat` app is not a target deliverable for v0.9

### 3.4 Refactor Discipline By Ring

In any single refactor round, exactly one ring may be the primary battleground. The other two rings may only receive passive compatibility work.

## 4. Current Reality vs Target Reality

### 4.1 Current Reality

- The browser runtime now lives under `apps/extension/src/*`; `apps/userscript/legacy/` is an archived reference only
- Gateway now uses the structured owner layout under `apps/gateway/src/{api,execution-kernel,tool-registry,tool-policy,builtin-tools,proposal-engine,shell-runtime,external-mcp,result-cache,audit-log,diagnostics,main}`
- Shared contracts and models already live in focused domain packages rather than the former monolithic protocol package
- Real runtime knowledge is currently strongest on the ChatGPT-page side

### 4.2 Target Reality

- `apps/extension` is the only supported browser app runtime path
- `apps/gateway` is the structured execution kernel
- Shared contracts and models live in dedicated packages
- `apps/userscript` remains an archived reference baseline only; it is not a live workspace member or supported runtime shell

Target-state documents must explicitly distinguish between "current implementation location" and "target ownership."

## 6. Module Ownership Map

### 6.1 Extension Modules

#### `chatgpt-adapter`

Owns:

- ChatGPT page facts
- DOM access abstraction
- Composer, message, and surface state extraction
- the canonical v0.9 code source for ChatGPT Web selectors, known request endpoints, and ignorable page-status patterns

Does not own:

- Tool execution decisions
- Gateway calls
- Result semantics

#### `injection-runtime`

Owns:

- Catalog bootstrap and refresh consumption
- Hidden injection payload creation
- Fallback injection path
- Injection status and diagnostics

Does not own:

- Assistant turn parsing
- Duplicate guard
- Tool execution

#### `turn-runtime`

Owns:

- Assistant turn normalization
- Invalid-turn classification
- Duplicate guard
- Startup/history rescan
- `ExecuteRequest` creation

Does not own:

- Tool execution
- Policy allow/deny
- DOM insertion

#### `result-delivery`

Owns:

- Turning `ResultEnvelope` into a deliverable payload
- Composer insertion
- Auto-send
- Delivery retry and copy-result fallback

Does not own:

- Tool execution semantics
- Proposal policy
- Execution history truth

#### `operator-panel`

Owns:

- Runtime snapshot display
- Operator intents
- Diagnostics entrypoints
- Mode switching entrypoints

Does not own:

- A second execution state machine
- Direct tool invocation bypassing runtime orchestration

### 6.2 Gateway Modules

#### `execution-kernel`

Owns:

- The only execution orchestration entrypoint
- Batch execution coordination
- Executor routing
- Result aggregation

Does not own:

- DOM or page facts
- Low-level policy rules
- Proposal internals
- Raw shell or external transport rules

#### `tool-registry`

Owns:

- Builtin and external tool aggregation
- Namespace resolution
- Materialized catalog production

Does not own:

- Per-call allow/deny decisions
- Tool execution

#### `tool-policy`

Owns:

- Workspace hard policy
- Mode-aware decision making
- Risk-aware action selection

Does not own:

- Tool execution
- Proposal creation
- Result rendering

#### `builtin-tools`

Owns:

- Structured builtin tool implementations

Does not own:

- Policy
- Final audit writing
- Runtime orchestration

#### `proposal-engine`

Owns:

- Proposal creation
- Proposal store
- Apply/discard flow
- Conflict recheck

Does not own:

- The decision that a call must become a proposal
- Operator UI

#### `shell-runtime`

Owns:

- `run_pwsh`
- Command guarding
- `cwd`/env shaping
- Timeout, stdout, and stderr capture

Does not own:

- Mode policy
- Workspace hard policy
- Final audit conclusions

#### `external-mcp`

Owns:

- External server lifecycle
- Transport adapters
- Raw tool proxying
- Error normalization

Does not own:

- Materialized visibility policy
- Final callable-state decisions

#### `result-cache`

Owns:

- Large result persistence
- Paging
- Lookup
- Expiry

Does not own:

- ChatGPT runtime concepts

#### `audit-log`

Owns:

- Execution audit events
- Policy audit events
- Lifecycle audit events

Does not own:

- Panel-specific formatting

#### `diagnostics`

Owns:

- Health snapshots
- Redacted copy bundles
- Aggregated operator diagnostics

Does not own:

- Execution control

## 7. Dependency Rules

### 7.1 Cross-App Rule

`apps/extension` and `apps/gateway` must not import each other's source files. They may only interact through:

- local transport
- shared contracts and models from `packages/*`

### 7.2 Extension Dependency Direction

Allowed direction:

```text
chatgpt-adapter -> page facts only
injection-runtime -> adapter + protocol models
turn-runtime -> adapter + turn/protocol models
result-delivery -> adapter + result models
operator-panel -> runtime snapshots + operator intents
```

Forbidden direction:

- Panel driving raw gateway calls that bypass runtime orchestration
- Turn runtime directly owning DOM insertion
- Adapter deciding whether tool calls are allowed

### 7.3 Gateway Dependency Direction

Allowed direction:

```text
api -> execution-kernel
execution-kernel -> tool-policy + tool-registry + executors
executors -> result-cache/audit-log through kernel-owned context
diagnostics -> aggregated read-only state
```

Forbidden direction:

- `api` calling builtin tools directly
- `tool-policy` executing tools
- Executors bypassing the kernel
- `diagnostics` becoming a second control plane

### 7.4 UI And Diagnostics Restrictions

- UI must not become an orchestrator
- Diagnostics must observe, not control
- Fallback paths must stay inside the same architecture

## 8. State Ownership Table

| State | Single owner | Primary consumers |
|---|---|---|
| workspace policy | gateway `tool-policy` | kernel, registry |
| materialized catalog | gateway `tool-registry` | injection runtime, panel |
| conversation execution profile | extension runtime storage | turn runtime, panel, gateway requests |
| latest open turn | extension `turn-runtime` | delivery, panel |
| duplicate guard state | extension `turn-runtime` | turn runtime |
| injection status | extension `injection-runtime` | panel |
| delivery status | extension `result-delivery` | panel |
| proposal store | gateway `proposal-engine` | kernel, operator-facing reads |
| execution history | gateway `audit-log` | diagnostics, operator reads |
| large result storage | gateway `result-cache` | kernel, diagnostics |
| external server lifecycle | gateway `external-mcp` | registry, diagnostics |
| trusted local / token / host policy | gateway config and policy | api, diagnostics |

Two ownership rules are especially important:

- Conversation execution profile is owned by the extension, not the gateway
- Materialized catalog is owned by the gateway, not synthesized locally by the extension

Execution-profile authority rule:

- The extension is the source of truth for conversation-scoped execution profile because it owns ChatGPT conversation-local runtime state
- The gateway must treat execution profile as request-scoped policy input, not as a UI hint
- The gateway may validate, constrain, or reject a requested profile through workspace hard policy, but it must not invent its own conversation profile truth
- Until a future shared persistence design exists, different browser tabs or conversations must be assumed to carry different profile state

## 9. Core Contracts Summary

The final system must stabilize these contract groups:

- `CatalogContract`
- `TurnContext`
- `ExecutionContract`
- `PolicyDecision`
- `ResultEnvelope`

Vocabulary mapping:

- `ExecutionContract` is the contract family that includes `ExecuteRequest` and `ExecuteResponse`
- `PolicyDecision` is the decision family that includes per-call `ToolDecision`

Summary invariants:

- Catalog is materialized truth, not raw registry output
- Turn context carries page-neutral execution context, not raw DOM details
- Execution is batch-first
- Policy decisions are explicit outputs
- Result envelopes remain structured and type-distinct

Minimum required contract surface for Phase 1:

- `CatalogContract`
  - must include a catalog version
  - must include materialized tool descriptors
  - must preserve current live catalog truth coming from `/tools` until an approved replacement exists
- `TurnContext`
  - must identify the assistant turn source
  - must include detection source
  - must include request-layer injection context
  - must carry conversation-scoped execution profile
- `ExecutionContract`
  - must be batch-first
  - must include a stable request id
  - must carry operator intent
  - must carry one or more normalized tool calls
- `PolicyDecision`
  - must distinguish execute vs proposal-required vs confirm-required vs deny vs skip
  - must include stable reason codes
  - must include a human-facing explanation
- `ResultEnvelope`
  - must distinguish inline tool result vs batch result vs proposal result vs cached reference vs execution error
  - must preserve the current `tool_result_batch` shape family as a first-class result type

Future detailed field-level definitions belong in `docs/protocols/*`, but agents must not wait for those files to exist before respecting the minimum contract surface defined here.

## 10. Critical Runtime Sequences

### 10.1 Hidden Injection Main Path

1. Extension obtains materialized catalog
2. User submits a prompt
3. Hidden request-layer injection applies the catalog contract
4. ChatGPT emits one or more `mcp` blocks
5. Turn runtime normalizes and validates the assistant turn
6. Extension builds `ExecuteRequest`
7. Gateway executes allowed calls
8. Gateway returns `ResultEnvelope`
9. Extension delivers the result back into the composer

### 10.2 Reviewed Proposal Path

1. Assistant requests a write-capable action
2. Gateway policy resolves it to proposal-oriented behavior
3. Proposal engine creates a proposal
4. Operator approves explicitly
5. Proposal apply runs as a second execution step
6. Result is delivered back to ChatGPT

### 10.3 Yolo Direct Execution Path

1. Conversation profile is `yolo`
2. Assistant emits stronger write, git, or shell actions
3. Workspace hard policy still caps what is allowed
4. Allowed calls execute directly
5. Side effects, stdout/stderr, and large outputs still go through audit and cache

### 10.4 External MCP Path

1. External server tools are normalized and materialized
2. Assistant calls an external namespaced tool
3. Kernel routes the call through the external MCP manager
4. Output is normalized back into the shared result model

### 10.5 Fallback And Recovery Path

If hidden injection, turn parsing, or result insertion fails:

- the failure must be diagnosed explicitly
- recovery must reuse the same contracts
- duplicate guard, policy, and audit must still apply

## 11. Capability Model

### 11.1 Capability Layers

- Builtin local workflow tools are the primary capability plane
- `run_pwsh` is the power-tool plane
- External MCP is the extension plane

### 11.2 Core Builtin Set

The final core should converge on at least:

- `read_file`
- `read_files`
- `list_directory`
- `search_files`
- `grep_files`
- `write_file`
- `patch_file`
- `git_status`
- `git_diff`
- `run_task`
- `run_pwsh`
- `mcp_list`

Interpretation rule:

- `write_file` and `run_pwsh` are core target capabilities, but they are mode-gated power tools rather than the default conservative workflow path
- `run_task` remains the preferred structured path for repeated and stable workflow actions
- `write_file` is not treated as a universal default write path; it coexists with proposal-oriented flows and stricter reviewed-mode handling

### 11.3 Extended Builtin Set

The extension ring may later include:

- `move_path`
- `copy_path`
- `delete_path`
- `create_directory`
- `create_file`
- `git_add`
- `git_commit`
- `git_restore_path`
- process lifecycle tools

### 11.4 Reviewed And Yolo

`reviewed` means operator-mediated execution:

- important side effects do not land automatically by default
- operator intent becomes an explicit workflow step

`yolo` means high-autonomy execution under workspace hard limits:

- stronger actions may run directly
- workspace hard policy still applies
- very high-risk actions may still require escalation

Mode precedence rule:

- workspace hard policy is the absolute ceiling
- each tool keeps a base policy envelope that may still force deny, confirm, or proposal behavior
- conversation mode selects the execution branch inside that envelope; it does not globally disable tool-level policy
- in practice, `yolo` may allow direct execution for some tools that are proposal-oriented in `reviewed`, but it does not imply that every write, shell, or external tool becomes unconditional
- external tools remain conservative by default unless their own materialized policy says otherwise

### 11.5 Builtin vs Shell vs External MCP

Use builtin when the action is:

- repo-local
- frequent
- structurally stable
- high-value for audit and display

Use shell when the action is:

- temporary
- highly compositional
- environment-specific
- not yet worth builtin modeling

Use external MCP when the action is:

- better served by an external tool ecosystem
- tied to third-party systems or non-core integration domains

## 12. Migration Boundaries

### 12.1 Refactor Order

Prerequisite gate:

- Use `TASK_STATUS.md` to confirm which v0.9 phase is actually active before treating the order below as today's implementation plan.

1. Freeze shared contracts and models
2. Extract extension runtime boundaries
3. Extract gateway execution kernel boundaries
4. Introduce mode-aware execution cleanly
5. Expand builtin capabilities
6. Mature proposal flow and external MCP

### 12.2 Current-to-Target Mapping

- The archived userscript runtime snapshot remains the raw reference for many target extension responsibilities
- The live gateway now routes through structured owner modules; only thin entrypoints remain above those boundaries
- Shared package growth is a prerequisite for stable app separation

### 12.3 Compat Deletion Conditions

Compat code may only be deleted once:

- target runtime logic exists
- target contracts are in use
- real-path verification exists
- compat no longer owns exclusive behavior
- any current live contract such as `/tools` has either remained canonical or has an explicitly approved migration path documented in task docs and product truth docs

Detailed deletion conditions belong in `docs/architecture/migration-boundaries.md`.

## 13. Codex Execution Rules

### 13.1 Single-Axis Refactors

Each non-trivial refactor round must have exactly one main axis:

- boundary extraction
- behavior stabilization
- capability addition

Mixing major boundary extraction and large capability expansion in the same round is forbidden.

### 13.2 Compat Rule

If a new behavior can only land in the compat layer first, that is a design failure signal. The refactor should stop and re-evaluate ordering instead of growing compat.

### 13.3 State Ownership Rule

Every new state must answer "who is the single truth owner?" before implementation begins.

### 13.4 Builtin Promotion Rule

If a shell use case becomes frequent, structurally stable, and high-value for audit or display, it should be reviewed for builtin promotion instead of remaining permanently in `run_pwsh`.

### 13.5 Stop Conditions

Refactor work must stop when:

- protocol semantics are still unclear
- a change crosses too many layers at once
- current behavior truth is inconsistent across docs, code, and runtime
- a second execution architecture is about to appear
- meaningful verification is unavailable
- a phase would invalidate the proven runtime baseline without an explicit migration path and re-verification plan

## 14. Acceptance Definition

The target architecture is only considered achieved when all four layers hold:

1. shared contracts are correct
2. module boundaries are correct
3. runtime integration is correct
4. real ChatGPT manual acceptance is correct

At the current repo stage, major architecture work must at minimum preserve or re-prove:

- hidden request-layer injection on the real page
- latest-open-turn startup rescan behavior
- invalid-turn enforcement behavior
- result insertion and auto-send behavior
- first-turn bootstrap behavior when catalog state is warm or cold

Passing lint, unit tests, or builds alone does not mean the architecture transition is complete.
