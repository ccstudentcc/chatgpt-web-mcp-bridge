## 3. Authorization State

As of April 27, 2026, the previous v0.1 real-page acceptance gate is closed. v0.9 is now the active mainline.

That does not mean every target-state surface should open at once. It means they are no longer blocked in principle by unfinished v0.1 close-out.

Active rule:

- v0.9 work is authorized
- each concrete slice still needs sequencing in root task-control docs
- current live contracts still need an explicit migration path before they are broken or removed

Current starting point:

- Phase 1 shared-contract freeze is already complete, and the declared Phase 2 Stage 7-21 slices are already closed
- Stage 21 `remove-compat-layers` is now formally closed after real ChatGPT Web validation of the extension-only runtime path in a real browser
- Phase 2.5 is the most recently completed follow-on slice: `WXT` shell convergence, popup/options addition, `React` + `Tailwind CSS` operator-facing UI, and extension capability-domain owner refactor were closed under one explicit design
- there is currently no active follow-on slice; start from `SPEC.md`, `IMPLEMENTATION_PLAN.md`, and `TASK_STATUS.md` before opening the next battleground
- start from `SPEC.md`, `IMPLEMENTATION_PLAN.md`, and `TASK_STATUS.md`
- do not open a new follow-on slice until those task docs deliberately declare the next battleground

## 4. How To Use This With Root Task Docs

If you are advancing the current repo:

- update `SPEC.md`, `IMPLEMENTATION_PLAN.md`, and `TASK_STATUS.md`
- keep them about the active v0.9 slice, gate, status, and handoff

If you are changing long-term product or architecture truth:

- update the relevant v0.9 doc under `docs/`
- keep root task docs synchronized on what changed in the active program

If you need the old runtime baseline:

- read `docs/prd.md`
- treat it as reference truth, not as the active product destination
